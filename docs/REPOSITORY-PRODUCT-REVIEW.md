## Вывод

У проекта уже есть инфраструктура удобного запуска. Следующий продуктовый шаг —
соединить установку, построение, сохранение, повторную локализацию и навигацию в
один проверенный сценарий. Новая камера и ещё один SLAM-бэкенд сами по себе этот
разрыв не устраняют. Целевое обещание: «Настрой Go2 один раз, сохрани карту и
используй её для повторных поездок; вычисления выполняются на Jetson».
Это целевое поведение, а не описание текущей готовности.

## Приоритеты

### 1. Проверить один полный сценарий и обозначить границы профилей

Сейчас основной 2D-профиль, экспериментальный 3D и D435i имеют разную степень
готовности. ROADMAP содержит незавершённые проверки save/reload/navigation
после изменения временной синхронизации. D435i не прошла спуск с возвратом;
текущие LiDAR-эксперименты также не дают основания обещать точную карту здания.

Сначала повторить цикл «построить → сохранить → перезапустить → загрузить →
задать начальную позу → выполнить A–B–A → отменить цель» на одном поддерживаемом
2D-профиле. Ручная начальная поза допустима в первом релизе. Отдельно проверять
3D на записи со спуском и возвратом; выбирать бэкенд по повторяемым результатам
на одних входах и отдельном контрольном маршруте. Не подменять геометрию карты
частотой сообщений или числом точек.

Результат: таблица профилей с местом вычислений, доступными действиями,
проверенными сценариями и ограничениями. 3D-экспорт PCD не обозначать как
готовую карту для загрузки в текущую slam_toolbox-localization.

### 2. Объединить существующие действия в один интерфейс команд

`mapping.sh` запускается с хоста, но сохранение и навигация документированы
командами внутри Docker и отдельным запуском relay/RViz. Предлагаемый интерфейс
(эти команды пока не реализованы):

```text
./go2 setup --robot ADDRESS
./go2 doctor
./go2 map start
./go2 map save office
./go2 maps
./go2 nav start --map office
./go2 status
./go2 stop
```

Использовать существующий supervisor, map_bundle и экспорт, сохранив совместимость
старых команд. `doctor` объединяет существующие проверки и сообщает проверенные
факты, но не присваивает карте точность по наличию ROS-топиков. Конфигурация
робота должна иметь один источник; сейчас адреса приходят из `.env`, окружения
контейнера и переменных отдельных установщиков.

Результат: полный сценарий выполняется с хоста без ручных SSH/Docker-shell команд.

### 3. Отделить бортовую сессию от окна просмотра

В текущем `mapping.sh` используется ожидание завершения SLAM или RViz, после
чего cleanup останавливает бортовую сессию. Это сознательно реализованный
сессионный режим, но он не удовлетворяет цели «ноутбук — только просмотр».
Предлагается отдельный бортовой жизненный цикл и возможность подключить RViz
повторно к уже идущему mapping. Сначала применить это к построению карты.
Поведение навигации при потере управления определить и проверить отдельно;
не переносить автоматически правило «продолжать» на команды движения.

Результат: закрытие RViz и повторное подключение не создают новую карту;
явная команда stop завершает нужную сессию и сохраняет её результат.

### 4. Библиотека карт и небольшая панель поверх готовых функций

Map bundle и 3D result.json уже существуют. Добавить единый индекс: имя,
превью, профиль, дата, версия сборки, поддержка локализации/навигации и связанные
логи. Сначала реализовать выбор и проверку карты в CLI, затем тонкую панель:
статус, карта, камера, выбор сохранённой карты, цель, отмена, завершение mapping.
Запись маршрутов и патруль уже есть — панели достаточно дать к ним доступ.
Браузерный просмотр может стать опцией; RViz остаётся доступным инструментом.

### 5. Подготовить воспроизводимый релиз

README сейчас совмещает laptop-2D, onboard-3D и ручные инструкции. ROADMAP
описывает D435i как ещё не начатую работу. Первая страница должна показывать
один рекомендуемый путь и явно отделять эксперименты. Подробную хронологию
сохранить в измерениях, а текущие настройки и ограничения вынести отдельно.

В CI есть build и изолированные тесты, но триггеры относятся к main и PR в main;
самостоятельные push экспериментальных веток не запускают этот workflow.
Собирать проверенные релизные образы для поддерживаемых архитектур, сохранять
версии/commit зависимостей и подтверждать установку на чистой системе. Добавить
инструкцию сбора диагностического архива из уже имеющихся логов и измерений.

## Первый объём работ

Первый PR: единая CLI-оболочка для существующего 2D-цикла, выбор сохранённой карты,
статус и диагностика; короткая актуальная инструкция. Критерий приёмки — другой
владелец выполняет цикл без подсказок автора. Параллельное исследование 3D остаётся
отдельным; результат поднимается в рекомендуемый профиль после проверки.

Следующие изменения: независимая бортовая mapping-сессия, бортовой запуск
нужных компонентов навигации, затем панель. Объединение камеры с LiDAR — отдельная
задача качества оценки движения, с калибровкой, общими timestamps и определённым
владельцем глобальной коррекции. В текущем Leg-KILO опубликованная поза уже
исправляется backend; её нельзя без анализа семантики считать непрерывной
локальной одометрией для второго оптимизатора.

Telecodex решает отдельную задачу управления сессией разработки. Его не стоит
делать обязательной частью запуска робота; можно выделить отдельно при упаковке.
